# SQLite Authorizer and Query Safety - Deep Dive Technical Analysis

This note documents the design, semantics, and implementation strategies for using SQLite's compile-time authorizer callback to enforce read-only access with table allowlists. The analysis is motivated by a class of bugs discovered in [[go-minitrace]] where regex-based table extraction fails on quoted identifiers and CTE aliases, and where the current approach leaks internal SQLite system tables such as `sqlite_master`. The primary recommendation is to move authorization from text-based parsing into the SQLite authorizer itself, which already parses the complete SQL and reports table names with full quoting awareness.

> [!summary]
> - The SQLite authorizer fires during statement preparation, not execution. This means the callback receives fully resolved table names including schema qualifiers, but never sees the runtime values bound to parameters.
> - `SQLITE_READ` is the action code for column reads. The table name argument is always the actual database object name, never a quoted token — the parser has already resolved it.
> - Regex-based table extraction fails on quoted identifiers, CTEs, and schema-qualified names. The authorizer does not have this problem because it operates on the parser's output.
> - Authorization through the authorizer provides defense in depth: it complements the read-only prepared-statement check, which only verifies that the query plan does not contain write opcodes.

## Why This Analysis Exists

The `go-minitrace` project exposes a query endpoint that accepts user-supplied SQL against an in-memory SQLite database containing minitrace sessions, turns, tool calls, and related data. The goal is to allow analysis queries to access only the minitrace tables while blocking access to system tables such as `sqlite_master` and `sqlite_temp_master`.

The current implementation uses a text-based approach: strip literals and comments, then use a regular expression to extract table names from `FROM` and `JOIN` clauses, and check each extracted name against an allowlist. This approach has two known failure modes:

1. Quoted identifiers such as `"sqlite_master"` are stripped to spaces by the literal remover, so the regex never sees them and the allowlist check is bypassed.
2. CTE aliases such as `WITH recent AS (...) SELECT * FROM recent` cause the regex to extract `recent` as a table name, which then gets rejected even though the query only accesses `sessions` — the CTE body.

These failures are not theoretical. Both have been reproduced with actual queries.

The deeper issue is that any text-based approach to SQL parsing inherits the fragility of trying to reason about structured syntax with pattern matching. The SQLite authorizer exists precisely to avoid this problem: it is invoked by the SQLite parser during compilation, and the arguments it receives are the already-parsed, resolved table names.

## How the SQLite Parser Produces Authorizer Events

The [architecture of SQLite](https://sqlite.org/arch.html) defines four major phases for statement execution:

1. **Interface** — the C API functions such as `sqlite3_prepare_v2()` receive raw SQL text.
2. **SQL Command Processor** — the tokenizer breaks the text into tokens, then the parser (generated by Lemon from `parse.y`) assembles those tokens into a parse tree.
3. **Code Generator** — the parse tree is traversed and bytecode opcodes are emitted into a `sqlite3_stmt` prepared statement.
4. **Virtual Machine** — the bytecode is executed by the VDBE.

The authorizer callback is invoked during phase 2 and phase 3. Specifically, it fires at various points during `sqlite3_prepare()` as the code generator traverses the parse tree. It is **not** invoked during execution (`sqlite3_step()`), except when `sqlite3_step()` internally re-prepares a statement after a schema change.

```
SQL Text ──→ Tokenizer ──→ Parser (Lemon) ──→ Code Generator ──→ Bytecode
                     │                   │                    │
                     │                   │                    └──→ Authorizer fires here
                     │                   └──→ Authorizer also fires during parse
                     └──→ Authorizer fires after tokenize for some operations
                          (e.g., ATTACH, DETACH, PRAGMA)
```

The key implication is that the authorizer operates on the *semantically resolved* form of the SQL. When the parser encounters `SELECT * FROM "sqlite_master"`, it has already recognized that the double-quoted identifier refers to the database object named `sqlite_master`. The authorizer receives `"sqlite_master"` as the table name argument, not `"" sqlite_master ""` or any intermediate representation.

This is fundamentally different from the regex approach, where `"sqlite_master"` appears as raw characters in the input text and gets handled by the literal stripper as a quoted string to remove.

## The Authorizer Callback Signature

The C API for registering an authorizer is:

```c
int sqlite3_set_authorizer(
  sqlite3* db,
  int (*xAuth)(void*, int, const char*, const char*, const char*, const char*),
  void* pUserData
);
```

The callback receives five arguments after the user data:

1. **op** — the action code, an integer constant such as `SQLITE_READ` or `SQLITE_INSERT`.
2. **arg1** — the first contextual string, whose meaning depends on `op`.
3. **arg2** — the second contextual string, whose meaning depends on `op`.
4. **arg3** — the database name (`"main"`, `"temp"`, or the name given by `ATTACH`).
5. **arg4** — the name of the innermost trigger or view responsible for the access, or `NULL` if the access is from top-level SQL.

The Go bindings in `github.com/mattn/go-sqlite3` expose this as:

```go
func (c *SQLiteConn) RegisterAuthorizer(callback func(int, string, string, string) int)
```

The Go bindings omit the user data pointer and the trigger/view argument, providing only `(op, arg1, arg2, arg3)` where arg3 is the database name. This is sufficient for most use cases, but the full C signature is worth knowing because arg4 (the trigger/view) can be useful for distinguishing direct user queries from trigger-fired access.

## The SQLITE_READ Action Code

`SQLITE_READ` is the most important action code for implementing read-only access with table restrictions. It is emitted for every column read that the query plan requires, including implicit reads of all columns in a `SELECT *` query.

The semantics are documented in the SQLite documentation:

- For a query like `SELECT count(*) FROM tab`, the authorizer is invoked once for that table with an empty column name.
- For a query like `SELECT name, age FROM tab`, the authorizer is invoked once per column, with `arg2` set to the column name each time.
- When a table is accessed through a view, the authorizer fires for the underlying table, not the view name.

The critical detail for this analysis is that `arg1` is always the *unquoted* table name. The parser resolves identifiers before the authorizer runs. This means:

```sql
SELECT * FROM "sqlite_master"
```

and

```sql
SELECT * FROM sqlite_master
```

both produce `SQLITE_READ` with `arg1 = "sqlite_master"`. The quoting in the source text is irrelevant to the authorizer.

This is the mechanism that fixes the first bug in the `go-minitrace` implementation: quoted identifiers that were invisible to the regex are fully visible to the authorizer because the parser has already consumed the quotes.

### Authorizer Events for Common Queries

The following table shows the exact sequence of authorizer events produced by representative queries against a database with a single table `sessions`:

| Query | Authorizer Events (operation, arg1, arg2) |
|-------|-------------------------------------------|
| `SELECT session_id FROM sessions` | `SELECT (NULL, NULL)`, `READ sessions session_id` |
| `SELECT * FROM sessions` | `SELECT (NULL, NULL)`, `READ sessions ROWID` |
| `SELECT s.session_id FROM sessions AS s` | `SELECT (NULL, NULL)`, `READ sessions session_id` |
| `SELECT name FROM sqlite_master` | `SELECT (NULL, NULL)`, `READ sqlite_master name` |
| `SELECT name FROM "sqlite_master"` | `SELECT (NULL, NULL)`, `READ sqlite_master name` |
| `SELECT name FROM 'sqlite_master'` | `SELECT (NULL, NULL)`, `READ sqlite_master name` |
| `UPDATE sessions SET title = 'x'` | `UPDATE sessions (NULL)`, `READ sessions title` |

Query 7 (single-quoted `sqlite_master`) is notable: in standard SQL, single quotes delimit string literals, not identifiers. The text `SELECT name FROM 'sqlite_master'` is syntactically invalid in SQLite for a FROM clause (a string literal is not a valid table source), so this query would fail during parsing before the authorizer is invoked. This is actually a defense-in-depth property: the parser rejects malformed SQL before any authorization check runs.

## SQLite System Tables and Their Authorizer Behavior

SQLite maintains metadata in system tables that live in the `main` schema. The most important are:

- **`sqlite_master`** — the permanent schema catalog. One row per table, index, view, and trigger.
- **`sqlite_temp_master`** — the temporary schema catalog. One row per temporary table, index, view, and trigger.

These tables are the primary targets for any table allowlist implementation. The goal is to permit access only to application tables (e.g., `sessions`, `turns`, `tool_calls`) and deny all access to system tables.

The authorizer approach handles this cleanly because the table name argument is always available. A simple allowlist lookup in the callback:

```go
func readOnlyAuthorizer(allowed map[string]struct{}) func(int, string, string, string) int {
    return func(op int, arg1, arg2, dbname string) int {
        switch op {
        case SQLITE_READ:
            if _, allowed := allowed[arg1]; !allowed {
                return SQLITE_DENY
            }
            return SQLITE_OK
        case SQLITE_SELECT:
            return SQLITE_OK
        default:
            return SQLITE_DENY
        }
    }
}
```

This function returns `SQLITE_DENY` for any `SQLITE_READ` event where the table name is not in the allowlist. It returns `SQLITE_OK` for `SQLITE_SELECT` and denies everything else. This is sufficient for read-only table restriction.

The `arg1` values that will appear for `SQLITE_READ` are the actual table names, normalized by the parser to match the names stored in `sqlite_master`. There is no quoting, no escaping, no case transformation — the name is exactly as defined in the `CREATE TABLE` statement.

## Defense in Depth: Multiple Layers

The `go-minitrace` implementation uses three independent layers of query safety. Each layer catches different classes of queries, and together they provide substantial protection.

### Layer 1: Read-Only Prepared Statement Check

The `ensureReadonlyPreparedQuery()` function uses the `sqlite3.Prepare()` API to obtain a prepared statement, then inspects its `Readonly()` flag. This flag is set by the SQLite code generator when the query plan contains only read opcodes (`OP_Column`, `OP_Rewind`, `OP_Next`, `OP_End`, `OP_ResultRow`, and related read-only opcodes). Any query plan that includes `OP_Insert`, `OP_Update`, `OP_Delete`, or DDL opcodes will have `Readonly() == false`.

This layer catches all write attempts regardless of how they are expressed: `INSERT`, `UPDATE`, `DELETE`, `CREATE TABLE`, `DROP INDEX`, or any other statement that modifies the database. It also catches subqueries and CTEs that contain writes, because the parser must analyze them during the compilation of the outer query.

However, this layer does not distinguish between different read-only tables. A query like `SELECT * FROM sqlite_master` is perfectly read-only and will pass the `Readonly()` check. The table allowlist is needed for that.

### Layer 2: SQLite Authorizer

The authorizer provides row-level and column-level access control on top of the read-only check. It is installed on the connection before query execution and removed afterward:

```go
conn.Raw(func(driverConn any) error {
    sqliteConn := driverConn.(*sqlite3.SQLiteConn)
    sqliteConn.RegisterAuthorizer(newReadOnlyAuthorizer())
    // query executes here
    sqliteConn.RegisterAuthorizer(nil)  // remove
    return nil
})
```

The authorizer operates at a finer granularity than the read-only check. It can allow `sessions` reads while denying `sqlite_master` reads, even though both are read operations. It can also deny access to specific columns of allowed tables, though this is rarely needed for the use case at hand.

The authorizer is installed on a per-connection basis using `conn.Conn()`, which obtains a raw connection handle that can be used for connection-level operations. This avoids the problem of the authorizer interfering with the database driver's own internal queries.

### Layer 3: Text-Based Allowlist Check

The `validateReadOnlySQLiteQuery()` function performs a preliminary check on the raw SQL text before the authorizer is invoked. It validates the query prefix (must start with `SELECT` or `WITH`), enforces the `ORDER BY` requirement when configured, and performs a regex-based table name extraction followed by an allowlist check.

This layer provides fast rejection of obviously disallowed queries before the database connection is acquired. It also provides an error message that references the source SQL text, which is more useful for debugging than an authorizer denial.

The problem with this layer is that it is the weakest link: the regex approach fails on quoted identifiers and CTEs, as documented. It should be kept as a fast-path filter for well-formed queries but should not be relied upon as the primary security boundary.

### Layer Interaction

The three layers execute in this order for each user query:

1. `validateReadOnlySQLiteQuery()` checks the raw text and returns an error if the prefix, statement count, or table names are invalid.
2. A raw connection is obtained from the pool.
3. `setSQLiteAuthorizer()` installs the authorizer callback on the connection.
4. `ensureReadonlyPreparedQuery()` prepares the statement and checks the `Readonly()` flag.
5. The query is executed via `QueryContext()`.
6. The authorizer is removed from the connection.

If the text-based check at step 1 passes but the authorizer at step 3 or the read-only check at step 4 fails, the error is returned without executing the query. This means the layers are *not* applied simultaneously during execution; they are applied sequentially, and each layer can reject a query before it reaches the next layer.

The practical consequence is that the regex-based layer provides the first rejection point for well-formed queries, while the authorizer provides the final authoritative check. If a query bypasses the regex (via quoted identifiers), it will still be caught by the authorizer because the authorizer operates on the parsed, resolved table names.

## Comparing Text Parsing and Authorizer Approaches

The table below compares the two approaches across the dimensions that matter for query safety.

| Dimension | Regex on Text | SQLite Authorizer |
|-----------|---------------|-------------------|
| Quoted identifiers | Missed or misclassified | Correctly resolved by parser |
| CTE aliases | Extracted as tables, causes false positives | Not emitted for CTE names, only for actual table reads |
| Schema qualifiers (`db.table`) | Regex must handle extra dot | Parser resolves to canonical table name |
| Subqueries | Regex must recurse | Authorizer fires for every table access |
| Views | Regex sees view name, not base tables | Authorizer sees base table names |
| Triggers | Not handled | Authorizer fires for trigger-fired reads |
| PRAGMA/ATTACH | Regex may miss | Authorizer sees the operation directly |
| Runtime cost | O(n) text scan per query | Zero extra cost — already runs during prepare |
| Error messages | Can quote source SQL | Only reports operation code and table name |

The authorizer approach is strictly superior for correctness. The text-based approach has the advantage of producing error messages that reference the source SQL text, which aids debugging. It also provides a fast rejection path that does not require acquiring a database connection.

## Implementation Pattern: Minimal Authorizer for Table Allowlists

The following Go code implements the recommended authorizer pattern:

```go
func newTableAllowlistAuthorizer(allowed []string) func(int, string, string, string) int {
    allowedSet := make(map[string]struct{}, len(allowed))
    for _, name := range allowed {
        allowedSet[strings.ToLower(name)] = struct{}{}
    }
    
    return func(op int, arg1, arg2, dbname string) int {
        switch op {
        case SQLITE_SELECT:
            return SQLITE_OK
        case SQLITE_READ:
            if _, ok := allowedSet[arg1]; ok {
                return SQLITE_OK
            }
            return SQLITE_DENY
        case SQLITE_FUNCTION:
            // Allow built-in and user-defined functions
            return SQLITE_OK
        case SQLITE_TRACE:
            // Allow TRACE if configured
            return SQLITE_OK
        default:
            return SQLITE_DENY
        }
    }
}
```

Key design decisions:

- The allowlist is converted to a `map[string]struct{}` at construction time. Lookups are O(1) and do not allocate.
- Table names are matched case-insensitively using `strings.ToLower()`. This matches the behavior of SQLite's internal name resolution, which is case-insensitive for identifiers (though case-preserving in `sqlite_master`).
- `SQLITE_FUNCTION` is explicitly allowed. Some queries use built-in functions that trigger authorizer events, and denying them would block otherwise valid queries.
- All other operations are denied. This includes `SQLITE_INSERT`, `SQLITE_UPDATE`, `SQLITE_DELETE`, `SQLITE_CREATE_TABLE`, `SQLITE_DROP_TABLE`, `SQLITE_ATTACH`, `SQLITE_PRAGMA`, and all DDL operations.

This authorizer is sufficient when combined with the read-only prepared statement check. The read-only check catches any attempt to prepare a write statement (which the authorizer would also catch, but the read-only check provides a clearer error message). The authorizer catches any attempt to access a disallowed table, even in a read-only query.

## CTE Behavior and Why Regex Fails

Consider the query:

```sql
WITH recent AS (
    SELECT session_id FROM sessions ORDER BY session_id DESC LIMIT 10
)
SELECT * FROM recent
```

The regex `(?i)\b(from|join)\s+([a-zA-Z_][a-zA-Z0-9_\.]*)` applied to the sanitized text produces two matches:

1. `from sessions` → extracted table: `sessions`
2. `from recent` → extracted table: `recent`

The regex correctly identifies `sessions` as the underlying table, but it also identifies `recent` as a table name, even though `recent` is a CTE alias, not a physical table. If `recent` is not in the allowlist, the query is rejected.

The authorizer does not have this problem. When SQLite compiles this query, it recognizes `recent` as a CTE alias and resolves all references to it to the underlying `sessions` table. The authorizer is invoked only for `SQLITE_READ` on `sessions`, never for `recent`. The `WITH` clause itself does not produce any authorizer event — CTEs are transparent to authorization.

This is because CTEs are a compile-time construct. SQLite expands CTE references into the query plan during code generation, and the authorizer fires during code generation. By the time the authorizer runs, there is no `recent` in the plan — only references to `sessions`.

The same logic applies to subqueries:

```sql
SELECT * FROM (SELECT session_id FROM sessions ORDER BY session_id LIMIT 10) AS subq
```

The regex would extract `subq` and `sessions`, but the authorizer only sees `sessions`. Subqueries are resolved by the parser before the authorizer runs, just like CTEs.

## Schema Qualifiers and Table Name Resolution

SQLite supports schema-qualified table names in the form `schema.table`. The `main` schema is implicit and does not need to be written. The `temp` schema is for temporary tables.

```sql
SELECT session_id FROM main.sessions
SELECT session_id FROM temp.temporary_table
```

When the authorizer receives `SQLITE_READ` for a schema-qualified name, the table name argument (`arg1`) is the canonical table name without the schema qualifier. The parser resolves `main.sessions` to `sessions` before the authorizer runs. This means the allowlist only needs to contain the table name, not schema-qualified names.

If a database is attached with `ATTACH 'file.db' AS extra`, then `extra.table` references a table in the attached database. The authorizer receives `arg1 = "table"` and `arg3 = "extra"` for `SQLITE_READ` on that table. The allowlist should contain the table name, and the schema qualifier in `arg3` can be used to restrict which attached databases are accessible.

## Trigger Behavior and Authorizer Events

Triggers introduce a complication: when a trigger fires, the SQL statements inside the trigger body are compiled and their authorizer events are checked. The authorizer receives the trigger name in the fourth argument (`arg4` in the full C API), which can be used to distinguish direct user queries from trigger-fired access.

The Go bindings omit this fourth argument, so code using the Go bindings cannot distinguish between a direct query and a trigger-fired query at authorization time. If the database schema contains triggers that read from tables not in the allowlist, those triggers will be blocked even though the user's direct query is allowed.

For the `go-minitrace` use case, this is acceptable because the database schema does not contain any triggers. If triggers were added in the future, they would need to be designed to access only allowed tables, or the authorization strategy would need to be revisited.

## Performance Characteristics

The authorizer callback is invoked once per operation per prepared statement, during the `sqlite3_prepare()` call. It is not invoked during query execution (`sqlite3_step()`). This means the performance cost of the authorizer is a one-time cost per query, proportional to the number of table accesses in the query plan.

For a simple query like `SELECT session_id FROM sessions ORDER BY session_id`, the authorizer is invoked approximately three times: once for `SQLITE_SELECT` and once for `SQLITE_READ` on the `sessions` table. For a query with multiple joins, the authorizer is invoked once per join table and once per column reference.

The map lookup in the allowlist check is O(1), so the per-invocation cost is negligible. The total cost of authorizing a query is dominated by the cost of parsing the SQL and generating the query plan, which happens regardless of authorization.

This is in contrast to the regex-based approach, which must scan the entire SQL text and produce matches even for queries that are rejected by the first few characters. The authorizer only inspects the tables that the query plan actually accesses.

## Implementation Recommendations

Based on this analysis, the recommended approach for implementing query safety in `go-minitrace` is:

1. **Keep the text-based prefix check.** Validate that the query starts with `SELECT` or `WITH` and contains no semicolons. This provides fast rejection and a useful error message. Remove the regex-based table name extraction.

2. **Implement the authorizer-based allowlist.** Use the minimal authorizer pattern shown above, with a case-insensitive table name map derived from `AllowedTableNames()`.

3. **Keep the read-only prepared statement check.** This is a necessary complement to the authorizer because it catches write attempts at the bytecode level, providing a second verification that the query plan does not contain write opcodes.

4. **Remove `stripSQLLiteralsAndComments()` from the validation path.** This function was needed for the regex approach (to prevent quoted strings from being misinterpreted as table names). It is no longer needed when the authorizer is the primary check. It can be kept for the fast-path prefix validation, but the sanitized output should not be used for table name extraction.

5. **Add tests for the authorizer behavior.** The current tests exercise the text-based validation path. New tests should verify that:
   - Quoted disallowed table names are denied by the authorizer.
   - Allowed table names are permitted regardless of quoting.
   - CTE aliases do not appear in authorizer events.
   - Schema-qualified names resolve to the correct table.
   - Write queries are denied by both the read-only check and the authorizer.
