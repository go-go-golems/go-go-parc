# PicoCalc Agenda — Measuring a cold Wasm build on the handheld

Typed Agenda opens its notes directory, reads the task file, and publishes a view. To measure whether the compiler makes this workflow interactive, the timer starts before reading typed source and stops when the kernel publishes the first file-backed frame. The ESP32-P4 creates a new compiler realm and a new WAMR instance for each run. The same experiment records how much heap compiling uses and how much time the frame-producing turn takes.

> [!summary]
> - Twenty optimized builds from bundled source reached the first frame in a median of 538 ms, with a 606 ms p95.
> - Five optimized builds from the editable notes file reached the frame in a median of 535 ms, with a 599 ms maximum.
> - Preserving the reactor's Wasm code as bytes reduced the median compiler heap peak from 1.36 MB to 407 KB. The host linker produced byte-identical Wasm.

## Compilation isn't the whole response

The firmware includes the compiler, editable-language runtime contract, and a prebuilt reactor. The reactor contains the SDK, I/O and lifecycle code. The editable program provides the task parser. On the P4, QuickJS compiles the program and links the result into the reactor. The world then starts as Agenda under the manifest, opens notes, and asks the filesystem worker for the file. Its settlement turn calls the generated parser and publishes the result.

```mermaid
flowchart LR
    Source["Read typed source"] --> Compile["Compile and link in a fresh QuickJS realm"]
    Compile --> Restart["Schedule and initialize a fresh WAMR world"]
    Restart --> Read["Read todo.txt using the notes claim"]
    Read --> Frame["Parse task records and publish frame"]
    Frame --> Panel["Compositor and physical display"]
```

The stopwatch ends at frame publication, just before the compositor and panel stages. This makes the two-second target testable on the board even when the keyboard fails. The physical keyboard controller in this session repeatedly returned I²C NACK. There is no measured physical keypress-to-visible-frame interval for this milestone.

The baseline and optimized serial runs used the same 22-world profile and existing 43-byte task file. Each steady series waited six seconds after opening serial to let the system settle. An unsynchronized first series had a 2.656-second outlier and is retained in the raw receipt. A separate complete system boot published its first Agenda frame 2.428 seconds after the application's compilation timer started. Other worlds were still initializing. The steady series and boot measurement reveal different scheduling conditions.

## Why byte representation mattered

The linker appends typed program functions after the reactor's existing imports and definitions. The reactor bodies can remain unchanged. Only the forwarding slot and the newly emitted definitions require generated bytes.

The baseline read every existing body into a JavaScript array of numbers, prepended its encoded length, then flattened the vectors into an intermediate array. All of that bookkeeping scales with the size of the reactor's code section. The optimized linker retains a view over each body's original length prefix and byte span. Then it calculates the outgoing code section size, allocates one byte array, and copies each segment once.

```text
for each old function body
    keep a byte view spanning the encoded length and body
replace the runtime parser slot with the generated forwarding body
append the compiled bodies
allocate the outgoing vector using the sum of segment byte lengths
copy the segments consecutively
```

The host test produced the same linked bytes before and after the change. It also exercised file authority, a parsed frame, a timer-triggered notification, and the persisted suppression record. The handheld builds emitted a 42,201-byte module in both configurations.

## Measurements

| P4 configuration after startup | Runs | Compile median | First-frame median | First-frame p95 | Compiler heap peak median |
|---|---:|---:|---:|---:|---:|
| Baseline linker, bundled source | 20 | 483 ms | 767 ms | 830 ms | 1,358,068 B |
| Byte-view linker, bundled source | 20 | 259 ms | 538 ms | 606 ms | 407,436 B |
| Byte-view linker, editable notes source | 5 | 261 ms | 535 ms | 599 ms | 407,336 B |

The nearest-rank p95 in the five-run sample is its maximum. The optimized bundled world's first frame-producing settlement took 2.45 ms at the median. The Wasm accounting was 147,456 bytes for linear memory and interpreter stack. Compiler heap means live bytes tracked by its QuickJS allocator. Neither figure is aggregate system memory.

An invalid edit returned a line and column with the Boolean type mismatch. The old world stayed available, and putting back the valid source produced a first frame in 524 ms. The firmware test used the app partition only. The valid test input remains available at `notes/agenda.typed`.

## Reproduction and scope

Project commit `2d1238c` contains the firmware bridge, linker optimization, script `05-measure-agenda-p4.py`, and exact per-run receipt in ticket `PICOCALC-AGENDA-COMPILER`. Build the reactor with `make -C picocalc-os agenda-reactor`, then build the ESP-IDF profile with `PICOCALC_TYPED_AGENDA=ON`. The `agenda baseline` and `agenda build` console commands exercise flash-bundled source and the editable file respectively. The keyboard and panel interval and the trusted RV32 backend have separate qualification gates.
