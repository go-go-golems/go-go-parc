# REPL Semantics, Scope, and Transformations in Interactive Programming Systems

## Formal semantics of interactive evaluation

Formal semantics in programming-languages research typically starts by defining the meaning of a *single* closed program phrase (an expression, a statement, a declaration) via an evaluation relation (operational semantics) or a meaning function (denotational semantics). A REPL becomes “formal” when we lift that single-step notion into a semantics of *sequences of interactions* where the meaning of step *i+1* depends on the state produced by step *i*. In other words: a REPL is best modeled not as a three-word slogan, but as a *state-transforming transducer* from an input stream of phrases to an output stream of printed results, threading a language-defined state (environments, stores/heaps, module tables, macro environments, type bases, etc.) across steps. citeturn9view0turn9view2turn9view1

A widely cited “textbook-formal” example of interactive semantics is the (formal) definition of Standard ML. entity["book","The Definition of Standard ML","milner 1990"] explicitly treats ML as interactive: a “program” is a *sequence of top-level declarations* whose execution *modifies the top-level environment* (called a *basis*) and reports changes to the user. It also splits each interaction into (at least) parsing, elaboration (static semantics), and evaluation (dynamic semantics), which is exactly the kind of multi-stage pipeline real REPLs embody. citeturn9view0

At the level of judgments, the same Standard ML definition makes the “threading” explicit: execution of a program is expressed as a relation that consumes an initial basis and state and produces an updated basis and state (schematically, something like `s, B ⊢ program ⇒ B', s'`). This is a canonical pattern for REPL semantics: each interactive phrase is executed in the current configuration and yields a new configuration for the next phrase. citeturn9view0

A second (and more modern) example is the mechanized CakeML line of work, where the REPL itself is given a top-level operational semantics in terms of a declaration-processing relation (e.g., a judgment that relates an input environment and declaration to an output environment), and then a REPL semantics that repeatedly reads declarations, evaluates them, and prints the *delta* of new bindings. Notably, that work also emphasizes the need to model divergence and failure *at the REPL level* (e.g., a declaration that diverges ends the observable output trace). citeturn9view2

A key methodological point for your article is that, once we formalize interaction as sequencing, we can treat “the REPL language” as distinct from “the batch language.” A recent paper on REPL interpreters argues that a REPL for a base language *L* often induces a related language *R* whose “programs” are sequences of snippets, and whose meaning is composition of snippet meanings (including effects). This perspective is useful for explaining why REPL behavior frequently diverges from “the language spec” in order to match user expectations: the REPL is, semantically, its own language layer. citeturn9view1

Finally, formal semantics forces you to decide what “read” and “print” mean *semantically*. In many real systems, “read” is not merely parsing; it includes incremental parsing, completeness checks, and sometimes recovery from incomplete input. Likewise “print” is not merely pretty-printing a value; it is part of the observable behavior and may include reporting newly introduced bindings or types (as in ML-family toplevels). These concerns appear explicitly in formal accounts that separate parsing/elaboration/evaluation phases and in REPL semantics designed around observable output traces. citeturn9view0turn9view2

## Environments, stores, and evaluation contexts

Most textbook semantics that aim to model stateful languages make a foundational distinction between an *environment* (names → something) and a *store* (locations → values). entity["people","Gordon D. Plotkin","pl theorist"]’s classic structural operational semantics (SOS) lectures/paper are a primary source for this separation: environments map identifiers to *denotable values* that may include locations, while stores map locations to *storable values*. In this formulation, assignment updates the store, while lexical binding extends (or shadows within) the environment. citeturn10search6

The terminology and conceptual split has deep roots in denotational traditions as well. entity["people","Christopher Strachey","pl theorist"]’s “Fundamental Concepts in Programming Languages” helped cement the idea of a “store” as the abstract model of mutable memory used by programming languages, distinct from syntactic naming. citeturn10search0

A crisp, pedagogy-oriented formalization appears in entity["book","Programming Languages: Application and Interpretation","krishnamurthi 2017"] by entity["people","Shriram Krishnamurthi","pl researcher"]: “the environment maps names to locations, and the store maps locations to values,” and interpreters for stateful features return not just a value but also an updated store (a “store-passing” style). This is exactly the shape you want when explaining REPL step-to-step continuity: each step consumes an `(env, store)` pair and produces a new one. citeturn3search3turn3search11

Classic interpreter textbooks align with this picture, but with different emphases:

- entity["book","Essentials of Programming Languages","friedman wand 2008"] (by entity["people","Daniel P. Friedman","pl researcher"] and entity["people","Mitchell Wand","pl researcher"]) is well known for developing semantics via executable interpreters and for introducing explicit store models to account for effects; course materials tied to the book frame “the store” (locations, references, assignment) and “store-passing specification” as a central semantic technique. citeturn20search0turn20search17  
- entity["book","Types and Programming Languages","pierce 2002"] by entity["people","Benjamin C. Pierce","pl researcher"] treats stores not only dynamically but also *statically* via **store typings**—a key idea for explaining type safety in the presence of mutation: evaluation runs on configurations ⟨term, store⟩ and preservation may require the store typing to grow monotonically as allocation occurs. (The book’s published table of contents explicitly calls out “Evaluation,” “Store Typings,” and “Safety” in the chapter on references.) citeturn21search19turn21search1turn21search5  
- entity["book","Semantics Engineering with PLT Redex","felleisen findler flatt 2009"] (by entity["people","Matthias Felleisen","pl researcher"], entity["people","Robert Bruce Findler","pl researcher"], and entity["people","Matthew Flatt","pl researcher"]) emphasizes **reduction semantics** and **evaluation contexts**—a style where “where evaluation happens next” is given by a context grammar, separating *search* for the next reducible expression from the *contraction* rules that perform computation. The current Redex manual continues to teach this “context grammar + reduction” decomposition as a practical engineering technique. citeturn20search5turn20search2turn3search2

Evaluation-context semantics is especially important for REPL design because “user expectations” about evaluation order and side effects are order-sensitive, and evaluation contexts are one of the cleanest formalisms for specifying (and variationally modifying) evaluation strategy. The foundational work by Felleisen and Hieb on syntactic theories of sequential control and state is a primary reference connecting evaluation contexts/reduction semantics to stateful and control effects. citeturn10search3

The environment/store split also clarifies what it means for a REPL to be “the same language” as batch evaluation. If a language’s core semantics is a relation like `(e, ρ, σ) → (e', ρ', σ')` (or big-step `⟨e, ρ, σ⟩ ⇓ ⟨v, σ'⟩`), then REPL semantics is typically the reflexive transitive closure of that relation, lifted to a loop over *top-level phrases* that update ρ and σ (plus the printed output). This is exactly the shape used in both SOS-style treatments and in concrete REPL formalizations like CakeML’s. citeturn10search6turn9view2

## Lexical and dynamic scope across language families

A scoping discipline determines how name occurrences (variable references) are resolved to bindings. In formal terms, it determines how the environment (or chain of environments) is consulted at a use site. A useful bridge between theory and practice is that many language references now explicitly define “scope” and “environment” in a way that matches textbook semantics: for example, the Python language reference defines scope as the visibility of a name within a block and calls the set of visible enclosing scopes “the block’s environment,” and it specifies resolution via the nearest enclosing scope unless overridden by `global`/`nonlocal`. citeturn12view1

### Scheme and the Lisp family

Scheme is specified as *statically (lexically) scoped*. The R7RS report explicitly characterizes Scheme as “statically scoped,” reflecting the long-running design choice that closures capture lexical environments and that name resolution depends on program text structure rather than call history. citeturn13search4

The Lisp family is historically central to the “dynamic vs lexical” story. Early Lisps commonly used dynamic scoping, and one of the destabilizing historical episodes was that some systems behaved differently in interpreted vs compiled code. entity["people","Kent M. Pitman","common lisp editor"]’s historical account notes that MacLisp used dynamic scoping in interpreted code and had a form of “lexical scoping” in compiled code that did not correspond to creating lexical closures in the way later Common Lisp users would expect—highlighting why mixed scoping regimes were a practical problem. citeturn1search20

Common Lisp ultimately standardized a hybrid model: **lexical variables by default**, with **dynamic (special) variables** available by declaration or proclamation. The Common Lisp HyperSpec defines dynamic variables via the `special` mechanism: a variable is dynamic if it is declared/proclaimed special, and the `special` declaration affects bindings and references accordingly. citeturn13search22turn13search6 The HyperSpec glossary also explicitly defines “lexical binding” as a lexical association between a name and its value, giving a specification-level vocabulary that matches PL-semantics textbooks. citeturn13search10

From a REPL-design point of view, this hybrid matters: in interactive Common Lisp development, dynamic variables (e.g., “current package,” printer controls, debugging parameters) are routinely rebound to control evaluation and printing behavior without rewriting code, which aligns with user expectations in a live image-connected workflow. Those expectations are reinforced by tool ecosystems that treat evaluation as incremental modification of a running system image. citeturn4search29turn13search22

### Python

Python’s scoping model is lexically nested at the level of blocks (modules, functions, classes), with explicit `global` and `nonlocal` mechanisms. The language reference formalizes name binding and resolution rules, including that local variables in a block can be determined by scanning the block for binding operations, and that free variables resolve via enclosing scopes (“nearest enclosing scope”), which is a direct operational account of lexical scope. citeturn12view1

Python interactive evaluation is also specified in a way that clarifies the REPL’s “persistent state”: each statement typed interactively is executed in the namespace of `__main__`, and interactive mode “reads and executes one statement … at a time.” This is essentially an environment-threading statement, but expressed in implementation-facing language. citeturn12view0

### JavaScript and ECMAScript

The ECMAScript specification offers one of the most explicit modern formal environment models in an industrial language spec. It defines **Environment Records** as specification objects that associate identifiers to variables/functions based on lexical nesting, with an `[[OuterEnv]]` link modeling lexical scope chains. citeturn6view2 This is extremely useful for textbook-style exposition because it aligns tightly with the environment notion in operational semantics, but with details necessary for JavaScript’s specific features (global object bindings, module environments, etc.). citeturn6view2

Crucially for interactive contexts, ECMAScript distinguishes *scripts* from *modules* in syntax and runtime semantics. In the scripts-and-modules chapter, the grammar for `ScriptBody` uses `StatementListItem[~Yield, ~Await, ~Return]`, while modules admit `StatementListItem[~Yield, +Await, ~Return]`, i.e., top-level `await` is syntactically permitted in modules but not in scripts. citeturn18view0

This spec distinction has REPL consequences: browser consoles and Node REPLs often aim to feel “module-like” for convenience (e.g., allowing top-level await), even when they are not evaluating actual ECMAScript modules. This is one concrete instance of the earlier principle that a REPL may define its own *snippet language* distinct from the standard batch language. citeturn9view1turn7view0turn5search28

### Tradeoffs for interactive use

Lexical scope is widely favored for local reasoning, optimization, and modularity: the meaning of a function can be understood from its definition site because free variables resolve through the captured lexical environment (as articulated directly in Python’s and ECMAScript’s environment models). citeturn12view1turn6view2 Dynamic scope, when available, provides a powerful mechanism for *ambient configuration* (debugging parameters, dynamic context like current I/O streams, thread-local settings), which is especially convenient in interactive debugging and REPL-driven exploration—hence its survival in Common Lisp via special variables. citeturn13search22turn13search6

But lexical scoping can introduce friction at the interactive top level when the language imposes “one-shot” rules on bindings. A vivid example is JavaScript’s `let`/`const` redeclaration rules (lexically declared names cannot be reintroduced in the same scope), which are sensible for programs but frustrating for a console. This is why developer consoles sometimes add nonstandard redeclaration affordances, effectively weakening or segmenting the “global lexical environment” across entries. citeturn5search28turn5search9

## Source-to-source transformation and hygienic rewriting

Source-to-source transformation (or AST-to-AST transformation) can be understood as a semantic strategy: rather than complicating the evaluator with many surface forms and interactive affordances, we *compile away* surface constructs into a smaller core language (often one chosen for semantic clarity). This is the same conceptual move as syntactic sugar elimination, macro expansion, CPS transformation, closure conversion, etc.—and it is also the move many interactive systems rely on to reconcile “language semantics” with “REPL ergonomics.” citeturn20search2turn10search3turn19search1

A helpful criterion for “transform vs modify evaluator” is whether the feature is primarily (a) *syntactic* and can be expressed as a local rewrite into existing constructs, or (b) *semantic* and requires new runtime behavior or new observable effects. Reduction-semantics frameworks (and tools like Redex) explicitly encourage the former: define a small kernel of reduction rules and specify derived forms as transformations into that kernel, while using evaluation contexts to enforce evaluation order. citeturn20search2turn10search3turn20search12

### What invariants must transformations preserve?

A textbook-grade way to say “the transform is correct” is **contextual (observational) equivalence**: replacing the original phrase with the transformed phrase in any program context does not change observable behavior. citeturn19search26 This standard is demanding, but it captures what REPL users implicitly expect when a system rewrites their input: debugging output and values may be formatted differently, but the meaning of the computation should not quietly change.

More operationally, the load-bearing invariants you listed correspond to well-established formal concerns:

**Binding structure and hygiene.** Any rewrite that introduces bindings or references must avoid accidental variable capture and must preserve lexical scoping. Hygienic macro systems were designed precisely to ensure this. The seminal “Hygienic Macro Expansion” work introduced an expansion discipline that prevents inadvertent capture and preserves intended binding structure. citeturn2search5turn2search1 Scheme standards subsequently specify hygiene and referential transparency properties for pattern-based macros (`syntax-rules`), including the key rule that introduced bindings are effectively renamed to avoid conflicts, and introduced free references resolve to the bindings visible at the macro definition site. citeturn13search9turn13search0turn2search0

**Evaluation order.** Transformations must preserve (or deliberately re-specify) evaluation order in effectful settings. Evaluation contexts make this explicit: they define the allowable decomposition of a term into context + redex, thereby determining left-to-right vs right-to-left evaluation and the points at which effects occur. This context/redex decomposition is presented as a core technique both in reduction-semantics tooling (Redex) and in explanatory literature on context-based operational semantics. citeturn20search2turn20search12turn10search3

**Type safety.** In typed languages, a transformation should generally be *type preserving* (or else come with a precise explanation of how typing changes). The classic syntactic method for type soundness formalizes safety via *progress* and *preservation* theorems over an operational semantics, providing a basis for proving that compilation and rewriting steps do not introduce “stuck” states. citeturn19search0 For stateful languages, this often requires coupling term typing with store invariants (store typings), as highlighted in typed treatments of references. citeturn21search5turn21search1

### Hygienic macros as the “gold standard” for scope-safe rewriting

Hygienic macro systems are, in a sense, the most mature industrialized form of scope-preserving source rewriting. Scheme reports and associated macro documentation emphasize that hygienic pattern macros preserve lexical scoping and avoid capture by renaming introduced identifiers and by resolving inserted free identifiers to the correct definition-site bindings. citeturn13search9turn13search0turn2search0

The `syntax-case` lineage (commonly associated with entity["people","R. Kent Dybvig","scheme designer"]) is a key reference point for more expressive hygienic rewriting: it supports pattern matching plus more general compile-time computation while maintaining hygiene by default. citeturn2search10turn2search22turn2search15 For REPLs, the connection is direct: a macro expander is an AST transformer that must preserve binding structure across expansions, and interactive systems must decide how macro environments evolve across incremental inputs (e.g., whether redefining a macro affects subsequent expansions only). R7RS explicitly discusses top-level macro definitions as extending the top-level syntactic environment for subsequent expansions. citeturn2search4turn13search0

In short: hygienic macro theory provides both vocabulary and correctness criteria for any REPL-driven AST rewriting that touches binding structure—whether you call it “macro expansion,” “desugaring,” or “interactive snippet normalization.” citeturn2search5turn13search0turn19search26

## Top-level await and asynchronous evaluation

Top-level `await` is where REPL semantics, scoping rules, and transformation strategies collide most visibly, because `await` changes not only *what* is computed but *when* execution can suspend and resume—and interactive systems must decide what it means to “evaluate the next input” while a previous input is suspended.

### ECMAScript: modules vs scripts and asynchronous module evaluation

ECMAScript makes top-level await fundamentally a *module* feature. The language spec encodes this in the grammar: scripts are parsed with `~Await` in statement lists, while modules allow `+Await` in their statement list items. citeturn18view0 This means that “top-level await” is not just a runtime behavior; it is a syntactic category distinction tied to the Script vs Module compilation unit. citeturn18view0turn17view3

Semantically, ECMAScript modules are evaluated via an `Evaluate()` operation that returns a **Promise**, and cyclic module records include internal fields such as `[[HasTLA]]` to mark whether a module is individually asynchronous (e.g., contains a top-level await). The spec’s module evaluation algorithms explicitly branch on whether `[[HasTLA]]` is true, executing some modules asynchronously (via `ExecuteAsyncModule`) and propagating fulfillment/rejection through dependent modules (`AsyncModuleExecutionFulfilled` / `AsyncModuleExecutionRejected`). citeturn18view1turn18view2 This provides a precise semantic explanation for a user-visible behavior: importers of an async module may need to “wait” for it to finish evaluating before its exports are ready. citeturn18view2turn5search10

### Node.js and browser consoles: “top-level await” as an interactive affordance

The Node.js REPL supports `await` “enabled at the top level,” printing the fulfilled value of awaited Promises, and documents that this support can be disabled via `--no-experimental-repl-await`. citeturn7view0 Importantly, Node also documents a semantic compromise: one known limitation is that REPL `await` “will invalidate the lexical scoping of the `const` keywords,” and it demonstrates a behavior where a `const` binding introduced with an awaited initializer can subsequently be assigned to (although redeclaration still errors). citeturn7view0 This is not a minor footnote: it is a concrete example of an interactive system bending lexical-binding discipline to accommodate asynchronous evaluation in a line-at-a-time REPL. citeturn7view0turn6view2

Browser DevTools consoles similarly support top-level await as a convenience feature for developers (allowing `await` without wrapping code in an async function). citeturn5search6turn5search10turn5search28 Combined with nonstandard redeclaration affordances (e.g., allowing `let`/`class` redeclaration across separate console inputs), this reinforces the point that consoles often implement a bespoke snippet semantics whose goal is interactive usability, not faithful execution of a single ECMAScript Script in the spec sense. citeturn5search28turn5search9turn17view3

### Python: language restrictions, compilation flags, and REPL-layer rewriting

In standard Python syntax, `await` is tied to async contexts (it is not ordinarily permitted “at the top level” of a module or interactive statement). However, Python’s toolchain explicitly acknowledges interactive/embedded use cases by providing a compiler flag: `ast.PyCF_ALLOW_TOP_LEVEL_AWAIT`, which “enables support for top-level `await`, `async for`, `async with` and async comprehensions.” citeturn23view0 This matters for your article because it shows a language/runtime exposing a controlled escape hatch: the *core evaluator* need not change, but the *compilation mode* can switch the accepted grammar and generated code shape. citeturn23view0turn8view0

IPython (used in many notebook contexts) takes the transformation approach explicitly: its documentation describes “Autoawait” behavior—if an `await` or other async construct appears at top level, IPython will automatically run it in a supported async loop environment so it can be awaited interactively, despite being a syntax error in the plain Python REPL. citeturn14search0turn14search8 IPython also documents input transformation hooks (string-to-string and AST-level mechanisms) that support syntax extensions and interactive conveniences, illustrating the general “transform the input” pattern for REPL design. citeturn14search7turn14search3

### Semantic challenges of mixing synchronous and asynchronous evaluation in a REPL

Top-level await forces REPLs to confront at least four semantic design questions, each with a direct mapping to formal semantics concepts:

**Step atomicity and sequencing.** In a synchronous REPL, each step transforms `(env, store)` into `(env', store')` and produces an output. With async, the step may produce a *suspended* computation that later resumes to complete the state update and output. ECMAScript addresses this by making module evaluation promise-based and by explicitly scheduling async module execution and dependency unblocking. citeturn18view1turn18view2 Node REPL addresses it by letting `await` run and by documenting scoping compromises that arise from fitting async suspension into a line-oriented environment. citeturn7view0

**Scoping and redeclaration rules.** If a snippet suspends mid-execution, when (and in what environment) are new bindings considered “in scope”? Node’s documented `const` anomaly under REPL await is one example of this tension. citeturn7view0 DevTools redeclaration affordances are another: to keep interactive iteration smooth, consoles may effectively create fresh lexical environments per entry or implement REPL-specific evaluation flags. citeturn5search28turn5search9

**Output ordering and observability.** Interactive systems must decide what is printed when: should intermediate outputs stream while awaiting? Jupyter’s message protocol is explicitly designed for this: execute requests can yield streams of outputs over time, and completion is a protocol-level notion (e.g., “idle” status) rather than a single return value. citeturn6view3turn14search5 This architecture aligns naturally with async semantics: “printing” becomes a sequence of observable messages rather than a single value display. citeturn6view3turn14search5
