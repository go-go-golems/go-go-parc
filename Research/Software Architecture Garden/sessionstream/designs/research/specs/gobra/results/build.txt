Positive verification

Result:

  INFO viper.gobra.Gobra - Gobra found 0 errors.

The verified contracts establish for the deterministic admission/close kernel:
- queue length remains in [0, capacity];
- capacity is stable;
- drop count is monotone;
- closing is sticky;
- a closed dispatcher rejects without state mutation;
- an open non-full dispatcher accepts exactly one item;
- an open full dispatcher increments drops exactly once;
- Close preserves capacity, queue length, and drops while making closing true;
- repeated Close is idempotent at the abstract-state level.

Combined-shell feasibility blockers

The requested production-shaped combination was probed directly against Gobra
v26.02:

  gobra -i probes/SelectDefault.gobra

reaches the frontend desugarer and fails with:

  scala.NotImplementedError: an implementation is missing
  at viper.gobra.frontend.Desugar$Desugarer.stmtD

The Gobra source also contains an explicit select-support TODO. Therefore the
actual guarded `select { case c <- item: default: }` admission cannot currently
be translated to Viper.

  gobra -i probes/Recover.gobra

is rejected with:

  error: got unknown identifier recover

Therefore callback panic isolation cannot be represented from the actual Go
construct either. `probe_unsupported.sh` checks both diagnostics and will fail
when a future Gobra version changes support, forcing reevaluation.

Scope limitation / hard stop

The kernel and primitive proofs cannot currently combine sync.Mutex,
nonblocking select/default admission, channel-close authority, goroutine
termination, callback panic recovery, and Wait synchronization into one
production-shaped Gobra proof. Modeling select or recover as trusted helper
contracts would move the two central obligations outside the proof and is not
accepted as completion evidence.
